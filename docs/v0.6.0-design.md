# v0.6.0 — sibling-wrapper model (no shim-by-default)

## Goal

Replace the shim-by-default install path with a **sibling-wrapper
model**. After install, `hermes` is always the real hermes
binary; users opt into policy enforcement by invoking `aw-hermes`
(a symlink to `agent0waste`) instead. The shim model is
preserved as an opt-in path for users who explicitly want
transparent interception.

The sibling-wrapper fixes the v0.5.0 UX problem: shimming
`hermes` by default means every `hermes` call is gated, which
makes the real binary second-class and the wrapper the default.
The sibling model inverts this — `hermes` is `hermes`,
`aw-hermes` is the policy wrapper, and which one you type
expresses your intent explicitly.

## Non-goals

- **Local LLM proxy** (#6): still deferred. The sibling-wrapper
  is the v0.6.0 work. LLM proxy becomes v0.7.0 (or later; no
  current use case driving the schedule).
- **Removing the shim path**: the shim at
  `~/.local/share/agent0waste/shims/hermes` continues to work.
  `agent0waste intercept enable hermes` continues to install
  it. Users who want transparent interception keep it.
- **Multi-binary support beyond hermes**: the design is generic
  (`aw-<cmd>` for any `<cmd>`), but v0.6.0 ships only
  `aw-hermes`. Adding `aw-claude`, `aw-cursor`, etc. is a
  copy-paste — deferred until someone needs it.
- **Bypass flag changes**: `--agent0waste-bypass` works
  identically on `aw-hermes` and the v0.5.0 shim. No new
  bypass syntax.
- **Linux/cross-platform support**: still macOS-only. Same
  scope as v0.5.0.

## The new model

**v0.5.0 (current):**

```
PATH: ~/.local/share/agent0waste/shims:$PATH

$ which hermes
/Users/me/.local/share/agent0waste/shims/hermes   # shim
$ which agent0waste
/Users/me/.local/bin/agent0waste                   # real binary
$ hermes --version                                 # → shim → policy → real
```

**v0.6.0 (new):**

```
PATH: ~/.local/bin:$PATH     # no shim hijack

$ which hermes
/Users/me/.local/bin/hermes   # real hermes (un-touched)
$ which aw-hermes
/Users/me/.local/bin/aw-hermes   # symlink → agent0waste
$ which agent0waste
/Users/me/.local/bin/agent0waste
$ hermes --version              # → real hermes (no policy)
$ aw-hermes --version           # → policy → real hermes
```

The user explicitly chooses: type `hermes` to get a clean call,
type `aw-hermes` to get policy-gated execution. No magic. No
PATH hijack. The shim path (`intercept enable hermes`) is
still there for users who want it; it's just not the default.

## Naming: `aw-hermes`

**Decision: `aw-hermes` is the canonical name.**

| Candidate | Pros | Cons | Verdict |
|-----------|------|------|---------|
| `aw-hermes` | Short, conventional (Linux tool prefix style — `gcloud-`, `kubectl-`, `aws-`), `aw` = "agent zero waste" | "aw" is also "angry walker" / "activity workshop" — context-free collision is unlikely but exists | **v0.6.0 ships this** |
| `intercept-hermes` | Describes the mechanism (interception), not the product | Verbose; "intercept" is implementation detail, not user-facing concept | Rejected |
| `hermes0waste` | Playful, ties to the "Agent0Waste" brand (0 = zero) | Confusing — reads as "Hermes's zero-waste mode" or "Hermes is a waste" | Rejected |
| `agent0waste-hermes` | Unambiguous, no abbreviation | Long (16 chars); every typing is a chore | Backup if `aw-` conflicts |
| `a0w-hermes` | Matches binary name `agent0waste` | `a0w` is opaque; users have to remember the brand spelling | Rejected |

The `aw-` prefix is generic enough to extend (`aw-claude`,
`aw-cursor`) without per-binary ceremony. It's also short
enough to be muscle-memorizable: 7 chars + the binary name.

## Distribution mechanism: symlink

**Decision: `aw-hermes` is a symlink to the `agent0waste` binary.**

```bash
# At install time:
ln -s "$(which agent0waste)" "$HOME/.local/bin/aw-hermes"
```

`agent0waste` inspects `argv[0]`. If it ends in `aw-hermes`,
it strips the `aw-` prefix and treats the remaining name
(`hermes`) as the target binary. Everything else
(`pick_decision`, cache, sandbox, exec) is unchanged.

**Why not a separate binary?** A separate `aw-hermes` binary
would be a thin shell wrapper that exec's
`agent0waste exec hermes "$@"`. That works, but it doubles
the install surface (two binaries to ship and update). The
symlink is a single install step and zero new code paths in
Rust.

**Why not a shell-script wrapper?** Macros / shell wrappers
have their own PATH resolution issues, slow startup, and
depend on `/bin/sh` (which is bash 3.2 on macOS, where
bash 4+ features are unavailable). The symlink is a
single syscall at install time and zero overhead at runtime.

**Path resolution:** the symlink target is the real
`agent0waste` binary (resolved at install). The agent0waste
binary reads `argv[0]` and uses the basename
(`aw-hermes`) to identify the wrapper name. We do **not**
rely on `realpath` of `argv[0]` — the user's
`$HOME/.local/bin` may be a symlink itself, and re-resolving
through it is brittle.

## What changes for users

**New install (v0.6.0):**

```bash
$ brew install agent0waste   # or: cargo install agent0waste
$ which hermes
/Users/me/.local/bin/hermes   # real
$ which aw-hermes
/Users/me/.local/bin/aw-hermes
$ aw-hermes --version          # policy-gated call
```

**Existing install (v0.5.0 → v0.6.0):**

```bash
$ agent0waste upgrade   # detects v0.5.0 install, runs migration
# Migration:
#   1. uninstall shim (intercept disable hermes)
#   2. create aw-hermes symlink
#   3. leave shim dir on disk; user can re-enable
# Result:
$ which hermes
/Users/me/.local/bin/hermes
$ which aw-hermes
/Users/me/.local/bin/aw-hermes
```

**Users who want the shim back:**

```bash
$ agent0waste intercept enable hermes
# restores shim at ~/.local/share/agent0waste/shims/hermes
# and asks: "also install aw-hermes? [Y/n]"
```

The shim and the symlink can coexist. `aw-hermes` always works
(policy-gated). The shim is opt-in for users who want every
`hermes` call to be policy-gated.

## argv[0] resolution — the implementation

```rust
// In src/main.rs (or a new src/wrapper.rs):

fn resolve_wrapper_target(argv0: &Path) -> Option<String> {
    let name = argv0.file_name()?.to_str()?;
    // Strip "aw-" prefix if present.
    name.strip_prefix("aw-").map(|s| s.to_string())
}

fn main() {
    let args: Vec<String> = std::env::args().collect();
    if let Some(target) = resolve_wrapper_target(Path::new(&args[0])) {
        // Invoked as aw-<target>. Treat as `agent0waste exec <target> <args>`.
        let mut new_args = vec!["agent0waste".to_string(), "exec".to_string(), target];
        new_args.extend_from_slice(&args[1..]);
        // Re-exec self with the canonical argv. The exec replaces
        // the current process so the symlink loop is broken.
        std::process::exec...  // (Rust exec semantics)
    }
    // ... normal agent0waste CLI dispatch
}
```

The argv[0] resolution is the only new code. Everything
downstream (`pick_decision`, cache, sandbox, exec) is
unchanged. The shim template and `aw-hermes` go through
**the same code path** — the shim is a shell wrapper that
calls `intercept check` and then exec's the real binary;
`aw-hermes` is a symlink that triggers the same `intercept
check` + exec flow via the `exec` subcommand. Same pipeline,
same audit log, same bypass flag.

## The `exec` subcommand

v0.6.0 adds a new top-level subcommand:

```bash
$ agent0waste exec hermes -- echo hello
# equivalent to: aw-hermes -- echo hello
# but invokable directly without a symlink
```

**What it does:**
1. Run the same `intercept check` for the target binary
2. Apply the same policy + sandbox
3. Exec the real binary

**Why expose it?** Three reasons:
1. **Testing**: smoke tests can run the policy path without
   needing a symlink (`tests/exec_smoke.rs`).
2. **Debugging**: `agent0waste exec hermes -- echo hello` is
   a verbose but explicit form for users debugging policy
   behavior.
3. **Symlink-free deployment**: in environments where users
   can't create symlinks (read-only `$PATH` dirs, sandboxed
   installs), they can call `agent0waste exec` directly.

The `exec` subcommand **always applies policy**. To bypass,
use `--agent0waste-bypass` (same as the shim):

```bash
$ agent0waste exec --agent0waste-bypass hermes -- echo hello
# or via the symlink:
$ aw-hermes --agent0waste-bypass -- echo hello
```

## Migration: v0.5.0 → v0.6.0

The upgrade command (`agent0waste upgrade`) detects the
v0.5.0 install and runs the migration:

| Step | Action | Reversible? |
|------|--------|-------------|
| 1 | Detect shim at `~/.local/share/agent0waste/shims/hermes` | n/a |
| 2 | `intercept disable hermes` (uninstall shim from active PATH) | yes — `intercept enable hermes` |
| 3 | `ln -s $(which agent0waste) ~/.local/bin/aw-hermes` | yes — `rm ~/.local/bin/aw-hermes` |
| 4 | Leave shim dir on disk; user can re-enable | yes |
| 5 | Print post-migration state: `which hermes`, `which aw-hermes` | n/a |

**No config migration needed.** `intercept.toml`,
`sandbox/<cmd>.sb`, and the heuristic cache are unchanged.

**The shim dir is left on disk intentionally.** Users who
want to roll back to v0.5.0 behavior can do so with one
command (`intercept enable hermes`) and have their shim
re-installed from the on-disk template.

## Open questions

1. **Should the upgrade be opt-in or automatic?** The
   migration is non-destructive (shim dir preserved,
   revertible). **Proposed automatic**: `agent0waste
   upgrade` runs it without prompting. Users who don't want
   it can re-install the shim with one command.

2. **What if `aw-hermes` is in a `~/.local/bin` that's not
   on PATH?** The install tries `~/.local/bin` first
   (matches the agent0waste binary's install location),
   then `~/bin`, then `/usr/local/bin`. The install prints
   the actual path and the user can adjust their shell rc
   if needed.

3. **Does `aw-hermes` need its own bypass audit log, or
   share the shim's `bypass.log`?** The log is at a
   well-known path (`~/.local/share/agent0waste/bypass.log`).
   Both the shim and `aw-hermes` write to it. No split —
   one log covers all bypassed calls across the install.

4. **What about non-macOS?** Same as v0.5.0 — out of scope
   for v0.6.0. The sibling-wrapper mechanism is
   cross-platform by design (symlinks + argv[0] work on
   Linux), but the build / install script is macOS-only.
   Linux users would need to install manually.

5. **Naming: `aw-` or `a0w-`?** `aw-` is the v0.6.0
   decision. If users find the abbreviation unclear,
   `a0w-hermes` is the documented fallback (in
   `docs/install.md`). We can also accept both as
   symlinks — the argv[0] parser strips either prefix.

## Out of scope reminder

This is **sibling-wrapper model only**. Local LLM proxy
(#6) is still deferred. v0.6.0 changes the *delivery
mechanism* for policy; it doesn't change the policy itself
(`pick_decision`, heuristics, sandbox, bypass — all
unchanged). The pipeline architecture from v0.4.0
(intercept → cache → heuristics → decision → sandbox → exec)
is preserved.

The bypass audit log, mode flag, and Decision::Deny from
v0.5.0 are unchanged. v0.6.0 is a UX / install change,
not a policy change.
