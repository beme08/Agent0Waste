# v0.4.3 — Layer 5: macOS sandbox-exec wrapper

## Goal

Wrap the real binary (hermes, in the dogfooded case) in
`sandbox-exec(1)` with a deny-default, allow-list profile so a
compromised or buggy hermes can't read arbitrary files, talk to
arbitrary hosts, or write outside its expected home-directory
scope.

## Non-goals

- Right profile for hermes specifically — v0.4.3 ships a
  reasonable conservative default; tightening the profile is a
  follow-up per hermes usage patterns.
- Linux equivalent (bubblewrap / landlock). Out of scope; the
  shim will detect non-macOS and skip Layer 5.
- Per-command auto-generation. The profile is a static file
  the user can hand-edit.
- Network policy beyond "allow outbound to the LLM provider
  hosts the binary is configured for." v0.4.3 allows all
  outbound network; a follow-up can scope it via SBPL
  `(remote tcp "api.openrouter.ai:443")` rules.
- Per-rule `cache_ttl_s` plumbing. Tracked separately as v0.4.4
  (mechanical, low urgency — all default rules use 30s today).

## Architecture: where Layer 5 sits

Layer 4 (intercept) and Layer 5 (sandbox) are orthogonal.
Layer 4 decides **whether** to run; Layer 5 decides **what the
run can touch**. The decision spec (docs/decision-spec.md) is
unchanged — Layer 5 is an execution wrapper, not a decision
layer.

```
shim args
  ↓
[Layer 4: intercept check]  ──→  decision
  ↓
[throttle sleep if needed]
  ↓
[Layer 5: wrap with sandbox-exec]   ← NEW in v0.4.3
  ↓
exec(real binary)
```

Layer 5 runs **after** the decision and **only on the exec
path**. Throttle, prompt, and the fail-open path all still
exec — they all get the same wrap.

## The profile (default for hermes)

Stored at `~/.config/agent0waste/sandbox/hermes.sb`. Based on
the sketch in #5, refined empirically against the real hermes
binary (a Python script → python3.11 binary with system
framework deps).

**Empirical finding (dogfood test):** hermes needs to read a
large number of system paths at startup (Python's stdlib
imports, system frameworks, dyld cache). Allow-listing read
paths is impractical and fragile. The actual security value
is in **write restriction** — hermes reading `/etc/passwd`
isn't the threat model; hermes writing to `~/Desktop/` or
`~/.ssh/` is.

```scheme
(version 1)
(deny default)

; --- Read: near-global (hermes reads a lot at startup) ---
(allow file-read*)
; Future v0.4.5+: deny read on (subpath "/Users/me/.ssh")
; and (subpath "/Users/me/.aws") for credential isolation.

; --- Write: allow-list only ---
(allow file-write*
  (subpath "/Users/me/.hermes")
  (subpath "/Users/me/.local")
  (subpath "/Users/me/.cache")
  (subpath "/private/tmp")
  (subpath "/private/var/folders")
  (subpath "/dev/null"))

; --- Network: outbound only (v0.4.3) ---
; v0.4.5+ scopes this to LLM provider hosts via
; (remote tcp "api.openrouter.ai:443") etc.
(allow network-outbound)
; (deny network-inbound) — hermes doesn't accept inbound.

; --- Process / IPC ---
(allow process-exec)
(allow process-fork)
(allow sysctl-read)
(allow mach-lookup)
(allow signal)
(allow system-socket)
(allow ipc-posix-shm-read* ipc-posix-shm-write*)
```

**Verified behavior** (dogfooded against the live hermes
binary at `/Users/me/.local/bin/hermes`):

| Operation | Under this profile |
|-----------|---------------------|
| `hermes --version` | exit 0, same output as unsandboxed |
| Write to `~/Desktop/sandbox-test.txt` | DENIED (`Operation not permitted`) |
| Write to `~/.hermes/sandbox-test.txt` | ALLOWED (own home dir) |
| `urllib.request.urlopen('https://httpbin.org/get')` | ALLOWED (status 200) |
| Inbound network | DENIED by default (no rule) |

## Configuration

`~/.config/agent0waste/intercept.toml` (existing file) gets
one new section:

```toml
[sandbox]
# Enable Layer 5 for the hermes shim. Default: false (opt-in).
enabled = false
# Path to the SBPL profile. Default: same dir as this toml, /sandbox/<cmd>.sb
# profile = "~/.config/agent0waste/sandbox/hermes.sb"
```

If `enabled = true` but the profile file is missing, the shim
prints a one-time stderr warning and runs unwrapped (fail-open,
matches the existing intercept check behavior on missing
config).

If `enabled = true` and sandbox-exec is unavailable (not
macOS, binary missing), the shim prints a warning and runs
unwrapped.

## CLI surface (command matrix)

Layer 4 and Layer 5 are **two separate opt-ins with orthogonal
lifecycles**. The shim's `SANDBOX_ENABLED` env var is baked at
install time; the toggle commands auto-reinstall the shim to
pick up the new env var. This avoids the shim re-reading config
on every exec.

| Command | Effect on shim | Effect on profile | Effect on config | Reversible by |
|---------|----------------|-------------------|------------------|---------------|
| `intercept enable <cmd>` | Installs shim (Layer 4); bakes `SANDBOX_ENABLED` from current config flag | None | Reads `[sandbox] enabled`; does not modify it | `intercept disable <cmd>` |
| `intercept enable-sandbox <cmd>` | If shim installed: re-installs with `--force` to flip env var. If not: prints hint, no-op | Writes default profile to `~/.config/agent0waste/sandbox/<cmd>.sb` (refuses if exists) | Sets `[sandbox] enabled = true` | `intercept disable-sandbox <cmd>` |
| `intercept disable-sandbox <cmd>` | If shim installed: re-installs with `--force` to clear env var | None (profile left in place) | Sets `[sandbox] enabled = false` | `intercept enable-sandbox <cmd>` |
| `intercept disable <cmd>` | Removes shim | None (profile left in place) | None (config flag preserved) | `intercept enable <cmd>` |

**Recommended first-time workflow** (Layer 4 + Layer 5):

```bash
$ agent0waste intercept enable hermes
# Installs shim, SANDBOX_ENABLED=0, no profile yet.

$ agent0waste intercept enable-sandbox hermes
# Writes default profile, sets enabled=true, re-installs shim
# (no-op if shim wasn't installed; prints hint).
# From this point: every `hermes` call goes through sandbox-exec.
```

**Toggle sandbox off temporarily** (keep profile for later):

```bash
$ agent0waste intercept disable-sandbox hermes
# Sets enabled=false, re-installs shim with SANDBOX_ENABLED=0.
# Profile is preserved at ~/.config/agent0waste/sandbox/hermes.sb.
# `intercept enable-sandbox hermes` re-enables with the same profile.
```

**Out-of-order calls are handled gracefully:**

- `enable-sandbox` before `enable` → writes profile + sets config
  flag, prints hint to run `enable`. Profile is ready when shim is
  installed later; `enable` will bake `SANDBOX_ENABLED=1` into
  the shim because the config flag is set.
- `enable` after the config already has `enabled = true` → shim
  is installed with `SANDBOX_ENABLED=1` from the start. No need
  to run `enable-sandbox` unless you want a default profile
  written.
- `enable-sandbox` called twice → second call is a no-op for the
  profile (refuses to overwrite). Re-installs shim with `--force`
  to ensure env vars are fresh. No error.

**Why env vars and not config read at exec time:**

The shim runs on every CLI call. Reading `intercept.toml` + stat-ing
the profile file at exec time adds 5-15ms of latency to the
hot path (we just spent v0.4.1 making this path sub-500ms). Baking
the state at install time keeps the hot path a single env-var
check. The cost is the `enable-sandbox`/`disable-sandbox`
auto-reinstall dance, which is a one-time hit per toggle.

**Symmetry check:**

| Toggle | Forward | Reverse |
|--------|---------|---------|
| Layer 4 (intercept) | `enable <cmd>` | `disable <cmd>` |
| Layer 5 (sandbox) | `enable-sandbox <cmd>` | `disable-sandbox <cmd>` |

The prefix `enable-`/`disable-` (with the hyphen) signals a
sub-feature of an already-installed shim. This matches the
existing `intercept migrate` subcommand's pattern (verb-only,
operates on an existing shim state).

## Shim integration

The shim currently does:

```bash
do_check() { "$AGENT0WASTE" intercept check ... ; }
case $(do_check) in
  0)   exec "$REAL" "$@" ;;            # allow
  64)  sleep COOLDOWN; do_check; exec "$REAL" "$@" ;;  # throttle
  65)  prompt; exec "$REAL" "$@" ;;    # prompt
  *)   exec "$REAL" "$@" ;;            # fail-open
esac
```

v0.4.3 wraps the `exec` calls:

```bash
maybe_sandbox() {
  if [ "$SANDBOX_ENABLED" = "1" ]; then
    exec sandbox-exec -f "$SANDBOX_PROFILE" "$REAL" "$@"
  else
    exec "$REAL" "$@"
  fi
}

case $(do_check) in
  0)   maybe_sandbox "$@" ;;
  64)  sleep COOLDOWN; do_check; maybe_sandbox "$@" ;;
  65)  prompt; maybe_sandbox "$@" ;;
  *)   maybe_sandbox "$@" ;;
esac
```

The shim reads `SANDBOX_ENABLED` and `SANDBOX_PROFILE` from
the env at startup (set by `intercept enable` when installing
the shim, or by the user in their shell rc if hand-installing).

## Trace interaction

`intercept trace` gets one new step at the end, mirroring
spec §3's step numbering extension. On a real `intercept run`
the trace would be visible only via debug logging (it doesn't
exec — that's the shim's job). For v0.4.3, the trace output
gains:

```
  [6] sandbox      enabled (profile=~/.config/agent0waste/sandbox/hermes.sb)
                  | disabled (default)
                  | skipped (non-macOS)
                  | skipped (sandbox-exec missing)
```

Step [6] is informational only — it doesn't affect the
decision or the cache. A future `intercept run --trace` could
write this to a per-call log for postmortem.

## Failure modes

| Failure | Behavior | Why |
|---------|----------|-----|
| sandbox-exec binary missing | stderr warning + unwrapped exec | Fail-open; matches intercept check contract |
| Profile file missing | stderr warning + unwrapped exec | Same |
| Profile parse error | stderr warning + unwrapped exec | Same |
| sandbox-exec returns non-zero | That exit code propagates to caller | The real binary failed; not our problem |
| Non-macOS | Layer 5 silently disabled | Out of scope for v0.4.3 |

The conformance rule from spec §3 ("cache is latency-only,
MUST NOT change decision outcome") doesn't directly apply to
Layer 5 — Layer 5 is not a decision layer. But the same
principle: **Layer 5 MUST NOT change the decision or the
real binary's input**. It can only restrict what the binary
can do.

## Tests

Unit (in `src/sandbox.rs`):
- Profile generation produces valid SBPL
- `enabled` flag is read from config correctly
- Missing profile → fail-open path

Integration (in `tests/sandbox_e2e.rs`):
- `hermes --version` under sandbox-exec → same output as
  without
- `hermes --version` under sandbox-exec with a profile that
  denies everything → exit code non-zero, "operation not
  permitted" in stderr
- `intercept trace --command "hermes --version"` shows
  `[6] sandbox enabled | disabled`

Manual validation (`docs/validation.md` v0.4.3 section):
- All v0.4.1/v0.4.2 paths still pass with Layer 5 disabled
- All paths pass with Layer 5 enabled
- One path with a restrictive profile (deny `/etc/shadow`) →
  hermes still works (hermes doesn't need /etc/shadow)
- One path that should be denied: try to read /etc/sudoers
  from inside the sandboxed hermes → denied

## Validation (dogfood checklist)

1. Install hermes shim with `intercept enable hermes` (no
   sandbox)
2. Verify 12 v0.4.1 paths still pass
3. Edit `intercept.toml`: `[sandbox] enabled = true`
4. Reinstall shim: `intercept disable hermes && intercept enable hermes`
5. Re-run 12 paths; verify same behavior + sandbox-exec
   visible in `ps`
6. Run `intercept trace --command "hermes --version"` →
   see `[6] sandbox enabled`
7. Edit profile to add `(deny file-read* (subpath "/etc"))`
8. Run hermes, verify `/etc` reads fail but normal hermes
   behavior works

## Open questions

1. **Path expansion in profile**: SBPL doesn't support
   `~`. We template `/Users/me/...` at install time. If
   `$HOME` is not `/Users/me` (CI, etc.), the profile is
   wrong. **Resolution:** v0.4.3 templates `$HOME` at
   shim install time. Document the limitation.
2. **Network scope**: Allow all outbound is permissive.
   Follow-up v0.4.5+ scopes to LLM provider hosts. **For
   v0.4.3 we accept permissive network** — Layer 5's value
   is filesystem containment, not network containment.
3. **Profile validation**: `sandbox-exec` parses SBPL
   lazily. A typo in the profile would only surface on first
   exec. Add a `intercept validate-sandbox <cmd>` subcommand
   in v0.4.3 that runs `sandbox-exec -f <profile> /bin/true`
   as a smoke test.
4. **Code signing / TCC**: macOS TCC (privacy controls)
   lives outside sandbox-exec. A sandboxed hermes still has
   whatever TCC permissions the user granted. We can't
   tighten that from inside the shim.
5. **What if hermes is in /opt/homebrew/bin instead of
   /Users/me/.local/bin?** The shim's `find_real` resolves
   it. The profile's `subpath` rules need to cover wherever
   it lives. v0.4.3 defaults assume `~/.local`; users with
   other install paths hand-edit the profile.
